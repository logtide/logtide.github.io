Authorization is a boundary, not a feature.

Field note • authZ • access control • telemetry

Claim: If authorization is implemented as “UI logic”, you don’t have authorization.

What goes wrong

  • Object ownership is not enforced server-side. The server trusts a user-supplied object id.
  • Role checks are inconsistent. One endpoint enforces, another forgets.
  • Indirect references leak. Guessable ids, sequential ids, weak UUID usage, verbose error messages.
  • Multi-step flows break. Step 1 checks authZ, step 2 forgets.

Developer rule

Every request that returns, updates, or deletes an object must perform:
1) authN (who is calling?) and
2) authZ (are they allowed to act on this object?), based on server-side policy.

Tester checklist (authorized environments only)

  • Identify objects: ids in path, query, JSON body, headers, nested fields.
  • Test horizontal authZ: same role, different user/tenant/object.
  • Test vertical authZ: low-priv user hitting admin-only actions.
  • Test list vs detail mismatch: list endpoint filtered, detail endpoint not.
  • Test create/update side effects: create under tenant A, access from tenant B.
  • Record: role, object id, response delta, status codes, data exposure.

Telemetry checklist (how defenders catch it)

  • Log: actor, tenant/org, object type, object id, action, authZ decision.
  • Alert on: one actor touching many object ids quickly (“object sweep”).
  • Alert on: repeated 403/404 bursts + eventual 200 (“probing then hit”).
  • Alert on: cross-tenant object access attempts (even when blocked).
  • Instrument: rate limits, anomaly scoring on object id cardinality.

Minimal regression tests

Add automated tests:
• user A cannot access user B’s object
• role X cannot call admin endpoints
• tenant A cannot read tenant B resources
These tests should run on every deploy.

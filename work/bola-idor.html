Case study: BOLA/IDOR in APIs

AppSec API Access control Offense-informed defense

Scope note: This writeup is based on authorized testing patterns. Target identifiers and sensitive data are removed. The goal is to show methodology, evidence structure, and remediation/regression thinking.

Executive summary

I tested object-level authorization in a multi-tenant API surface. The core question: does the server enforce ownership/tenant policy for every object access?

The failure mode is common: the API accepts an object id and returns data without verifying the caller is permitted to act on that object. This is often called BOLA (Broken Object Level Authorization) / IDOR.

Threat model

  • Actors: authenticated user (low privilege), optionally within tenant A
  • Assets: invoices, documents, profiles, orders, tickets (any object with an id)
  • Boundary: tenant boundary + per-user ownership
  • Impact: unauthorized read / update / delete depending on endpoint

Methodology (repeatable)

  • Inventory endpoints that take object ids in path/query/body.
  • For each endpoint, capture a baseline request as user A.
  • Obtain a valid object id belonging to user B / tenant B (in authorized test envs).
  • Replay the request as user A with the object id swapped.
  • Compare response: status code + body + side effects.
  • Record authZ decision evidence: 200 vs 403/404, metadata leaks, and any write impact.

Evidence pattern (sanitised)

Example endpoint shape (sanitised):

GET /api/v1/invoices/{invoice_id}
Authorization: Bearer <token>

Expected (secure behavior):

  • user A requesting user B’s invoice → 403 (forbidden) or 404 (not found), consistently
  • no sensitive metadata leakage (owner email, totals, addresses, etc.)

Observed (vulnerable pattern):

  • user A can fetch invoice belonging to user B by swapping {invoice_id}
  • response includes fields that confirm ownership and reveal sensitive details
// Request as user A (token_A) with invoice_id belonging to user B:
GET /api/v1/invoices/INV-100492
Authorization: Bearer token_A

// Response (200 OK) contains:
{
  "invoice_id": "INV-100492",
  "owner_user_id": "USER-B",
  "tenant_id": "TENANT-B",
  "amount": "...",
  "billing_details": "...",
  ...
}

Why this is enough evidence: The server returned a protected object for an unauthorized actor. That’s the boundary failure.

Impact

  • Confidentiality: unauthorized access to other users’/tenants’ data
  • Integrity: if any update/delete endpoints share the same pattern, attacker may alter or remove data
  • Escalation: object access can reveal identifiers enabling chaining (emails, references, internal ids)

Root cause (typical)

  • Authorization implemented as “filtering lists” but not enforced on “get by id”.
  • Service layer fetches by id only: SELECT * FROM invoices WHERE id = ?
  • Missing policy check: AND tenant_id = caller.tenant_id or ownership check.

Remediation (what to change)

  • Enforce server-side object-level policy on every endpoint that touches an object.
  • Prefer centralized authorization (policy function / middleware) rather than “remembering to check”.
  • Bind object fetch to actor context:
    • getInvoice(invoice_id, caller) not getInvoice(invoice_id)
  • Avoid exposing internal ids; use non-guessable identifiers, but do not treat that as authorization.
  • Return consistent errors (403 vs 404) based on your disclosure policy, but be consistent.

Regression tests (what prevents reintroduction)

  • Tenant A cannot access Tenant B objects (read).
  • Tenant A cannot update/delete Tenant B objects (write).
  • User A cannot access User B objects within same tenant, if ownership applies.
  • List endpoints and detail endpoints must enforce the same policy.

Blue-team notes: how to detect abuse

  • Log authZ decision: allow/deny + reason + object id + actor + tenant.
  • Alert on high cardinality object id access by one actor (object sweep).
  • Alert on repeated deny bursts followed by allow (probing then success).
  • Alert on cross-tenant object access attempts even if blocked (it’s attacker behavior).
